# MQTT 5 conformance

natsmqtt5 aims to be a conforming MQTT 5.0 Server. This file records where it stands against the
specification's numbered conformance statements, and is what [ROADMAP.md](ROADMAP.md) is ordered
from.

- Specification: [MQTT Version 5.0, OASIS Standard, 7 March 2019](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html)
- Reviewed: 2026-10-09, against v0.11.2 plus the changes after it (see the CHANGELOG's
  `[Unreleased]`). Re-run when the code or the specification has moved a lot.
- Data: [`conformance/mqtt5-statements.tsv`](conformance/mqtt5-statements.tsv), one row per
  `[MQTT-x.y.z-n]` statement. The statement texts are in the specification; the file carries the
  ids, sections and findings.

## Where it stands

**No statement is VIOLATED or UNSURE.** A test fails if a row says so without this file listing it
(`TestNoConformanceStatementIsViolatedOrUnsure`), and there is none to list.

Every statement id in the specification was extracted (252 distinct). The table carries one row
each, and the rows are regenerated from the tests, not written from memory: a row is TESTED only
if every test it names exists and cites the statement's id in its name, doc comment or body
(`TestEveryConformanceRowIsBackedByATestThatCitesIt`), and an id a test cites must be one the
specification has (`TestEveryStatementIDATestCitesIsInTheTable`). The counts below are generated
from the table between the markers and checked against it
(`TestTheCountsInConformanceMdAreTheTables`); after the rows change, run
`UPDATE_CONFORMANCE=1 go test -run TestTheCountsInConformanceMdAreTheTables .`.

Most of the work behind these counts was integration tests that drive the broker over a real TCP

## Not implemented, and why it is allowed

These are features the specification lets a Server leave out. A statement behind one is
NOT-APPLICABLE, and the row names the feature's [ROADMAP.md](ROADMAP.md) entry and a test that
shows the broker refusing or not advertising it the way the specification requires.

- **Enhanced authentication (AUTH packets).** A CONNECT with an Authentication Method is refused
  with 0x8C Bad authentication method, which the specification gives for a method the Server does
  not support (§3.1.2.10, §4.12). The AUTH statements cannot be reached.
- **WebSocket transport.** The specification names TCP, TLS and WebSocket as examples of a
  transport and requires only an ordered, lossless stream (§4.2); WebSocket statements (§6) bind a
  Server that offers it.
- **QoS 2 on shared subscriptions.** A QoS 2 request on a `$share/` filter is granted QoS 1,
  reported in the SUBACK, which [MQTT-3.8.4-7] permits.
- **Server-to-client Topic Aliases.** The broker never sends one; the Client's Topic Alias Maximum
  is what permits it and a Server may use none.
- **Statements whose wording a request cannot violate** (for example, "the Server MUST NOT send X
  unless the Client asked for it" when the broker never sends X), which the table also marks
  NOT-APPLICABLE with the reason and the test that shows the premise.
- **Statements that bind only a Client** are CLIENT-ONLY: nothing a Server does can break them.

The broker does not promise more than this list. Optional behaviour a SHOULD asks for and the
broker lacks is on the roadmap (for example `$` topics by default, a client over its Receive
Maximum, topics with whitespace).

## What it found, as history

The first review (2026-10-07, v0.9.0) found 19 statements violated and several the broker did
not meet in corners. Each was fixed with a test that cites it; this is where each shipped. The
CHANGELOG has the full text.

- **v0.9.1.** A client could publish to `$retained/<topic>` and replace the retained message for
  `<topic>`, bypassing the Authorizer, and read the offline queue through `$queue/#`.
  [MQTT-3.3.1-8].
- **v0.10.0.** QoS 1 and 2 messages published while a session was disconnected were dropped unless
  `OfflineQueue` was on, while the CONNACK said Session Present=1. The queue is on by default
  whenever the broker uses JetStream. [MQTT-3.1.2-23], [MQTT-4.5.0-1].
- **v0.11.0, shared subscriptions.** A disconnected shared-subscription member kept receiving, and
  dropping, its share: QoS 1 and 2 work now goes only to connected members, through a backlog in
  the offline queue [MQTT-4.5.0-1], [MQTT-4.1.0-2]. An unacknowledged QoS 1 message stays in the
  backlog until its PUBACK and goes to another member when the session ends; [MQTT-4.8.2-6] is held
  by the same tests. A shared subscription whose last member left kept its backlog; it is deleted
  with the subscription (`shared_ends_test.go`).
- **v0.11.0, catching up.** A client that fell behind lost QoS 1 and 2 messages [MQTT-4.1.0-1]; a
  connection that dropped while behind lost what was waiting, and the resume replay gave up after
  30 seconds [MQTT-3.1.2-23], [MQTT-4.5.0-1]. A detached session nobody resumed kept its NATS
  subscriptions for the life of the broker; a sweep now expires it, never before its interval has
  passed (`sessionsweep_test.go`).
- **v0.11.0, Message Expiry.** The interval was forwarded and never enforced. It is now enforced,
  and the remaining interval reduced, on every delivery path. [MQTT-3.3.2-5], [MQTT-3.3.2-6],
  [MQTT-4.3.3-7].
- **v0.11.0, protocol errors.** A SUBSCRIBE with No Local on a `$share/` filter, a PUBLISH carrying
  a Subscription Identifier, and a Response Topic with a wildcard were accepted or answered with a
  code that is not allowed; each is now a DISCONNECT 0x82 (CONNACK 0x82 for a Will).
  [MQTT-3.8.3-4], [MQTT-3.3.4-6], [MQTT-3.3.2-14], [MQTT-4.13.1-1]. A retained message could carry
  its publisher's Topic Alias to a subscriber [MQTT-3.3.2-11]. A CONNACK, PUBACK, PUBREC or
  DISCONNECT over the client's Maximum Packet Size was discarded whole; the Reason String and User
  Properties are dropped first [MQTT-3.2.2-19], [MQTT-3.2.2-20], [MQTT-3.4.2-2], [MQTT-3.5.2-2],
  [MQTT-3.14.2-3]. A PUBLISH could be written after the broker's DISCONNECT [MQTT-3.14.4-1]. A Reason
  Code returned by an `Authenticator` that Table 3-1 does not list for a CONNACK is sent as 0x80
  [MQTT-3.2.2-8].
- **v0.11.0, Wills.** The Will of a broker killed outright was never published; with
  `DurableWills` a surviving broker publishes it once, after the Will Delay Interval. The ids
  [MQTT-3.1.2-7] to [MQTT-3.1.2-10] were one sentence out of place in this repository's data and
  were corrected.
- **v0.11.0 to v0.11.1, restoring a session.** A restored session resent nothing it had in flight
  and forwarded a resent QoS 2 PUBLISH twice; the record now keeps each unacknowledged message's
  identifier, QoS state and queue sequence, in the record when its PUBLISH is 16 KiB or less and
  in a bucket of its own above that, and a message with no queue copy travels with it. A
  connected session checkpoints its replay position (`Options.SessionCheckpointInterval`), so a
  session whose broker was killed does not repeat up to a day of messages; a QoS 2 message sent to
  a client is recorded before its PUBLISH and before its PUBREL go out. Proved with a real SIGKILL
  of `cmd/natsmqtt5` (`killed_*_test.go`). [MQTT-3.1.2-5], [MQTT-3.1.2-23], [MQTT-4.3.3-6],
  [MQTT-4.3.3-10], [MQTT-4.3.3-12], [MQTT-4.4.0-1], [MQTT-4.5.0-1].
- **v0.11.1.** The Will belongs to the connection that set it, so a reconnect cancels the
  displaced connection's Will and a live client's Will is not published (`will_ownership_test.go`)
  [MQTT-3.1.2-8], [MQTT-3.1.2-10], [MQTT-3.1.3-9]. A broker cut off from NATS closes its clients
  before a survivor publishes their Wills (`nats_partition_test.go`) [MQTT-3.1.2-8]. A live copy
  delayed past the replay rewind is still replayed, on any broker (`late_live_copy_delay_test.go`)
  [MQTT-4.4.0-1]. A resend's send-quota slot stays with the copy (`resend_quota_test.go`)
  [MQTT-3.3.4-9]. A withdrawn Packet Identifier survives a restart or kill [MQTT-4.4.0-1],
  [MQTT-2.2.1-4]. A success CONNACK is shortened to fit a small Maximum Packet Size
  (`small_connack_test.go`) [MQTT-3.1.2-24], [MQTT-3.2.2-16], [MQTT-3.3.2-12]. A data race
  between `Broker.Close` and a late live copy is gone.
- **After v0.11.2.** A client with more QoS 2 PUBLISH packets unacknowledged than the Receive
  Maximum the CONNACK stated was served; it is now sent DISCONNECT 0x93 and the connection is
  closed. The specification's sentence for this (§3.3.4) has no statement id of its own, but §4.13.1
  lists 0x93 among the Protocol Error codes and a Server that detects one MUST close the connection
  [MQTT-4.13.1-1]; the row for [MQTT-3.3.4-7], which binds the client, now also carries the tests
  of the Server half. The broker first read this as a courtesy, which it is not.
- **After v0.11.1.** A shared SUBSCRIBE that raced the last member's leaving was refused;
  the joiner now retries the consumer's creation until the old one is gone (§4.8.2, the life of
  the subscription, which has no statement id). The conformance table itself is
  now regenerated from the tests and guarded. Two statements the review marked as met only
  by reading now have a test: [MQTT-3.2.2-1] (the reserved bits of the CONNACK flags are
  zero) and [MQTT-3.2.2-20] (a CONNACK carries no User Properties the client did not allow).

Two inherent limits were found and left, and both are in the CHANGELOG: an acknowledgement that
arrives after a resend carries the same Packet Identifier as the resend's own, so the broker counts
it as the copy's; and under 5 bytes no CONNACK fits a Maximum Packet Size, so it is discarded
[MQTT-3.1.2-25].

One deviation from a SHOULD remains by default. MQTT 5.0 §4.7.2: "The Server SHOULD prevent Clients
from using such Topic Names to exchange messages with other Clients" (no statement id). The broker
refuses only the two levels its own data lives under (`$retained`, `$queue`) unless
`RestrictDollarTopics` is set, because refusing every `$` topic would break applications using
`$app/...` today; proven by `dollar_topics_test.go`. It is on the roadmap.

## Keeping it current

Re-run the review when the code or the specification has moved a lot. When a fix lands, cite the
statement it addresses in the test that proves it, and update its row here.
